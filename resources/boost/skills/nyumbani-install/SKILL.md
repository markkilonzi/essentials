# Nyumbani Install

`php artisan nyumbani:install` is the one command that sets up and refreshes a Nyumbani app. It is safe to run again. On an interactive run it asks Boost's first-time questions and two optional ones of its own, both defaulting to no: `Set up a basic portal?` and `Run the migrations now?`. With `--no-interaction` it never asks. Composer runs it on `post-update-cmd` as `nyumbani:install --no-interaction --ansi`, so a `composer update` brings the newest rules and skills.

## What it does, in order
1. **Dependencies.** Installs `laravel/boost --dev` if it is missing, and requires `nyumbani/daraja`, `nyumbani/messaging` and `nyumbani/dt-tables` in the app's own `composer.json` if the app only gets them through Essentials. Boost reads guidelines and skills only from packages the app requires itself, so indirect ones are invisible to it. Then it runs itself again in a fresh process, because the new classes are not loaded in the first.
2. **Rules.** Copies the Nyumbani rules to `.ai/rules/nyumbani-*.md`, replaces older copies, removes ones the package no longer ships, and rebuilds `.ai/rules/index.md`. Never edit them; the next run overwrites them.
3. **Config and migrations.** Publishes `essentials`, `daraja`, `messaging`, `permission`, `activitylog` and `dt-tables` config files if absent (a freshly published `dt-tables.php` is set to the `tailwind` theme with `btn btn-sm btn-primary` buttons and `rounded-lg border px-3 py-1.5 text-sm` inputs and selects; an existing one is never touched) (Essentials registers the `dt-tables-config` tag, since the data tables package has none). Everything the installer puts in the app from the package goes through `vendor:publish` tags: the configs, the migrations (`essentials-permissions-migration`, `essentials-permissions-group-migration`, `activitylog-migrations`) and the starter `permissions.json` (`essentials-permissions`), so each can also be published by hand with `php artisan vendor:publish --tag=...`, and the activity log migration. The permission tables come from Essentials' own migration, which already has the `group` column; an app that published Spatie's migration earlier gets a small `update_permissions_table_add_group_column` migration instead. It never publishes a migration the app already has.
4. **App files, only what is missing.** Adds blank package keys to `.env.example` (never `.env`), the `@node-modules`, `@public`, `@resources`, `@vendor`, `@storage`, `@enums`, `@data-tables` and `@config` aliases to `resolve.alias` in `vite.config.js` (only the missing ones, checked with Node before the file is kept, and skipped with a note when the config has its own `resolve` setting or no `defineConfig`), the theme `@import` to `resources/css/app.css` (written with the `@vendor` alias when `vite.config.js` has it, else the relative `../../vendor` path, and moved to the alias on a later run) with the `@source` lines for `app/Enums`, `app/DataTables` and `config/dt-tables.php` (Tailwind finds classes written in those PHP files only through them), the scripts `import` to `resources/js/app.js` (plus `Livewire.start()` there, when the file does not start Livewire, because nothing in the page starts Alpine otherwise), a starter `database/seeders/data/permissions.json`, and the `discord` channel in `config/logging.php`.
5. **Basic portal (optional).** Asks `Set up a basic portal?` on an interactive run (default no), or runs without asking with `--portal`; a non-interactive run without the flag skips it. Publishes the `essentials-portal` tag (`admins/pages/dashboard.blade.php`, `admins/partials/sidebar.blade.php`, `layouts/app.blade.php`, never overwriting a view the app already has: `vendor:publish` runs without `--force`), whose sidebar is a Dashboard link plus a Docs group linking the Essentials, Daraja, Messaging and DtTables docs (local only), then, while the `HasHomeRoute` checklist item is not done (so it stays quiet once the app has the route and the contract), prints what is left for the developer to do: a route for the dashboard, `Route::view('dashboard', 'admins.pages.dashboard')`, inside the `auth` group in `routes/web.php` (any route name; the sidebar link uses `user()->homeRoute()`, so `homeRoute()` must return that route's URL) and the user model changes (`HasHomeRoute` + `homeRoute()`, `HasDefaultPermissions`, `Impersonate`); it edits no PHP file. With the portal, the `HasHomeRoute` checklist item also needs a dashboard route, found by scanning the registered routes for one that shows `admins.pages.dashboard` (or runs an app-owned `Admins\DashboardController`), so it passes whatever the route is named or wherever it lives.
6. **Build.** Runs `npm run build` when the app has a `package.json` and `node_modules` (otherwise notes that `npm install` comes first). A failed build is reported and does not stop the install.
7. **Migrations (optional).** On an interactive run, when the permission and activity tables are missing, asks `Run the migrations now?` (default no). A yes runs `php artisan migrate`, so the roles and permissions sync in the same run; a non-interactive run never asks and never migrates.
8. **Roles and permissions.** Syncs the roles and permissions from `permissions.json` with `php artisan nyumbani:permissions`, only once the permission tables exist. On a first run where the migrations did not run (you answered no, or it was non-interactive) it says so and waits for the next run.
9. **Storage link.** Links `public/storage` when a configured link is missing.
10. **Pint.** Runs `vendor/bin/pint` on only the PHP files the installer published or edited (configs, migrations, `config/logging.php`), never the app's own code; skipped when the app has no Pint.
11. **Boost.** The first time (no `boost.json`) it runs `boost:install`. Always, it loads the four Nyumbani packages into `boost.json`, lists their skills there (`boost:update` installs only the skills named in `boost.json`, and finds new ones only by asking, which a non-interactive run cannot), sets the agent to `claude_code` when none is set (a non-interactive first install picks none, and `boost:update` refuses to run without one), then runs `boost:update`.
12. **Checklist.** Prints a table of done, optional and to-do items.
13. **Docs invitation.** Ends with a panel linking the Quick start and the docs of Essentials, Daraja, Messaging and DtTables (built from the registered docs, so the links always match the real routes).

## Reading the checklist
| Item | Fix when it is not done |
| --- | --- |
| Livewire started in `app.js` | Import `Livewire` from `../../vendor/livewire/livewire/dist/livewire.esm` and call `Livewire.start();`. Without it Alpine never starts and the modals, tabs and playgrounds do nothing. |
| Theme / scripts imported | Add the one line the table names to `app.css` / `app.js`. |
| User model implements `HasHomeRoute` | Implement `Nyumbani\Essentials\Contracts\HasHomeRoute` and return a URL from `homeRoute()`. Once the portal is published this one item becomes `User model implements HasHomeRoute and the dashboard has a route` and also needs a route that shows `admins.pages.dashboard` (`Route::view('dashboard', 'admins.pages.dashboard')`, any name, any routes file) inside the `auth` group in `routes/web.php`; its fix names only what is missing. |
| User model has roles and default permissions | Use `Nyumbani\Essentials\Traits\HasDefaultPermissions`. **Not** `Spatie\Permission\Traits\HasPermissions`: it has no roles and no `assignDefaultPermissions()`. |
| User model can be impersonated | Use `Lab404\Impersonate\Models\Impersonate`. |
| Migrations have run | Run `php artisan migrate`, or answer yes to `Run the migrations now?` on the next interactive run. The installer publishes migrations and runs them only when you say yes. |
| Laravel Boost is installed | Run the installer; it requires Boost for you. |
| Boost is set up with the Nyumbani packages | Run `composer require nyumbani/daraja nyumbani/messaging nyumbani/dt-tables`, then the installer again. |
| Basic portal | Optional: run `php artisan nyumbani:install --portal` to publish the dashboard, layout and sidebar. |
| discord log channel, Daraja credentials, Connect settings | Optional: needed only if the app uses that feature. |

The installer reports; it never edits the user model, the routes or any other application code. It only adds the configuration, build and framework files described above, and the portal's files, none of which it overwrites.

## Rules for changing the installer
- Every step must be idempotent: add only what is missing, and leave anything the app already has.
- Do not run `migrate` unless the developer answers yes to the interactive question (never in a non-interactive run), do not run `composer` for anything but the dependencies above, and never touch `.env`.
- A step that edits a file must still leave valid PHP (the logging step checks this before saving).
- When a step is added or changed, update the Installation docs table, this skill, the checklist in `Console/Support/InstallChecklist.php` and the tests in `InstallCommandTest.php`. The tests fake `vendor:publish`, `storage:link` and Boost's commands so nothing writes into the real project.
